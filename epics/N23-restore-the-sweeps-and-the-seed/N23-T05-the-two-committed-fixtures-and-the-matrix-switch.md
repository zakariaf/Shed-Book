## 5. What you build

### 5.1 The two commits, in order

**Commit 1 — `test(fixtures): the two seeded fixtures, generated`.** Two files and nothing else:

```
test/fixtures/flock_400_3seasons.json
test/fixtures/flock_15_at_cap.json
```

The commit message carries the **exact commands** that produced them, including the seeds, so a
reviewer can reproduce the bytes rather than read them:

```
dart run --define=SHED_SEED=true tool/seed.dart --ewes 400 --seasons 3 --seed 42 --out test/fixtures
dart run --define=SHED_SEED=true tool/seed.dart --ewes 15  --seasons 1 --seed 15 --out test/fixtures
```

`00-README` §7.4 puts a golden re-baseline in its own commit because *"it is a deliberate act, never
bundled with the change it re-baselines"*. A generated fixture is the same class of artefact and gets
the same treatment: a diff that is 100 % generated JSON beside a diff that is 100 % test code, rather
than one diff nobody can read.

**Commit 2 — `test(fixtures): switch the matrix and the budgets to restoreFixture`.** The code.

### 5.3 The signature

```dart
// test/support/seeds.dart — the ONLY fixture loader. There is no second one.
/// Loads a committed backup file into an ALREADY-OPEN in-memory database,
/// through RestoreService.importInto — 12 §5.2, decision #74: "it makes the
/// fixture loader a continuous test of the one code path where a bug loses
/// five seasons."
///
/// It calls half one of the restore (the import + the validation) and never
/// half two (the file swap), because an in-memory database has no file to
/// rename. That split is N23-T01 §5.2 and this function is why it exists.
Future<void> restoreFixture(AppDatabase db, String name) async { … }
```

There is no `jsonDecode` in this function beyond parsing the file into the `tables` map that
`importInto` takes — and specifically no second insertion path, no `db.into(...).insert` loop, and no
"fast path for tests". That is the whole reason the anchor test is in this task rather than in N13.

### 5.4 The details that are easy to get wrong

- **A bespoke loader is the obvious shortcut and it is the defect.** Writing thirty lines that
  `jsonDecode` the fixture and insert rows directly would work, would be faster, and would delete the
  reason the fixtures exist. Decision #74: routing the loader through the restore path *"makes the seed
  script a continuous test of the one code path where a bug loses five seasons."* A second loader is a
  second migration surface nobody exercises until the night it matters.
- **Assert row counts, not a return value.** A `restoreFixture` that fails silently — a mistyped table
  name, a swallowed exception, a transaction rolled back — leaves every matrix cell rendering the
  *empty* layout, which is smaller and cannot overflow. All 144 cells go green and prove nothing.
- **The count stays derived.** R58: *"the arithmetic must follow the variant list, not a remembered
  number."* At this point in the build order `kPumpableVariants` holds the variants N13–N21 have added;
  it reaches fourteen at N33-T01. Do **not** write `expect(kPumpableVariants.length, 14)` and do not
  write today's number either — the self-check computes the product from the same lists the loops
  iterate.
- **The harness comment says N23-T05, not N23-T06.** Critique **S3** and N13-T07's §1 both say
  *"N23-T06"*; the task that lands the fixtures and switches the matrix is **this one**. N13-T07 already
  carries the correction. Verify the comment, fix it if it drifted, and then update it to say the
  switch has happened — a ledger that still promises a future switch after the switch is a ledger
  someone will act on twice.
- **Do not regenerate the fixtures when the schema bumps.** The committed files carry
  `"schema": <kSchemaVersion at generation>`, and `04 §6.5` accepts a backup whose schema is *lower*
  than the app's. That makes these two files the only standing evidence in the repo that an older
  backup still restores — which is the exact scenario a shepherd hits in 2029. Regenerating them
  silently deletes that evidence and changes the input of four later epics in one commit. If a
  migration genuinely makes a fixture unloadable, the fix is `importDefaults` (`09 §5.6`), not a
  regeneration.
- **`flock_400_3seasons.json` contains no reminder rows**, and that is not a bug. The critique records
  it: the fixture is generated one epic before reminders exist. N24 handles it. Do not "fix" it here
  and do not regenerate later — see the row above.
- **The at-cap fixture is exactly at the cap, and `setEwesInCurrentSeason` survives.** `12 §5.3` is
  explicit: *"the fixtures ship at or under the cap, and decision #90's assertion is written at 99."*
  The helper that tops a season up to *n* ewes is what writes the 99-ewe case; deleting it because a
  fixture arrived breaks the monetization test.
- **Two fixtures, and the list is closed.** *"Do not add a third fixture without deleting one"*
  (`12 §11.5`). Four topics depend on populated state and none of them needs a bespoke shape; a fixture
  per test is how a suite becomes unmaintainable.
- **The fixtures are committed, not generated in CI.** `00-README` §7.1 lists them by name. Generating
  them on the runner would make the matrix depend on the seed script being green, which inverts the
  dependency: the fixtures are an *input*, and an input you regenerate is not an input.
- **Every cell still builds its own database.** The `test` job runs
  `--test-randomize-ordering-seed random` (#121). `restoreFixture` mutates the database it is handed,
  so hoisting one fixture-loaded database into a `setUpAll` makes every cell depend on the order it
  ran in — and the failure surfaces as a flake at 11pm on release day.
- **Loading a 400-ewe fixture per cell is slower than a `seeds.dart` helper.** That is expected and
  accepted: `12 §5.2` says fixtures are for *"anything asserting shape at volume"*, which is precisely
  what the matrix is. If the suite time becomes a problem, the answer is the `slow` tag's 3× timeout,
  never a smaller fixture.
- **The two fixtures are large files in a git diff.** Review them the way `00-README` §7.3 says to
  review generated code: read them only to confirm nobody hand-edited one. The reviewable artefact is
  the **command in the commit message**, not the JSON.

## 6. Constraints that bind this task

- **Offline** — no network path may be added. G2 (the dependency allowlist) and G3 (the import scan) stay green, and the permission set never changes without G0's recorded evidence.
- **Vocabulary** — one word per concept (`CLAUDE.md`). The banned words are banned in the commit message too: no `draft`, no `save()`, no `sync`, no `Error` as a failure name.
- **This task authors no string and no widget**, so the ARB rule binds it negatively: a string in this
  diff means a screen was edited to make a cell pass, which is `12 §6.3`'s *"fix the layout, never the
  matrix"* read backwards.
- **Nothing under `lib/` changes.** If a file under `lib/` appears in either commit, stop and find out
  why. A fixture that needs a production change to load is a fixture that is testing the wrong thing.
- **Generated artefacts are never hand-edited** (`00-README` §7.3). If a fixture is wrong, fix the
  generator and regenerate — in its own commit, with the command in the message.
